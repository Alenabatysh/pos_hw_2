# Модуль «ПОС» (Преподавательская Оценка Студентов)

## 1. Архитектура проекта
Выбрана **Clean Architecture (Чистая архитектура)**. Правило зависимостей соблюдено строго: зависимости направлены только внутрь (к Domain).
* `Domain` — Ядро (Entities, VO, Domain Services, Порты). Не зависит ни от чего.
* `Application` — Use Cases. Зависит только от Domain.
* `Infrastructure` — Адаптеры (JSON, CSV). Зависит от Application.
* `Console` — Точка входа (UI, DI-контейнер). Зависит от всех слоев.

**Стрелка зависимостей:**
`Console` ? `Infrastructure` ? `Application` ? `Domain`

## 2. Domain-Driven Design (DDD) 

### Ubiquitous Language
В коде используются термины предметной области: `Student`, `Criterion`, `Evaluation`, `Rubricator`, `Score`, `Weight`.

### Entity vs Value Object
* **Value Objects (VO):** `StudentId`, `CriterionId`, `Score`, `Weight`, `StudentName`. 
  * *Обоснование:* Это неизменяемые значения. Два объекта `Score(5)` равны друг другу, у них нет уникального ID. Они валидируют себя прямо в конструкторе (например, `Score` не может быть отрицательным), что защищает домен от создания невалидных данных.
* **Entities (Сущности):** `Student`, `Criterion`, `Evaluation`. 
  * *Обоснование:* Имеют уникальный идентификатор (Id) и жизненный цикл. Сравниваются по ID. Например, если студенту изменить имя, это будет тот же студент.

### Границы агрегатов (Aggregate Roots)
1. **`Student`** — корень агрегата.
   * *Обоснование:* Оценка (`Evaluation`) не существует в отрыве от студента (это факт "этому студенту поставили балл"). Поэтому `Evaluation` — это сущность внутри агрегата `Student`. Мы не можем сохранить оценку, не сохранив студента. Список оценок приватный (`_evaluations`), изменить его можно только через метод `AddEvaluation()`, который проверяет инвариант: *нельзя поставить две оценки по одному критерию*.
2. **`Rubricator`** — корень агрегата.
   * *Обоснование:* Критерии живут независимо от студентов. Рубрикатор защищает инвариант: *нельзя добавить два критерия с одинаковым ID*.

### Инварианты (Бизнес-правила, которые охраняет модель)
1. Балл (`Score`) не может быть отрицательным (защищено в VO).
2. Оценка не может превышать максимальный балл (`MaxScore`), установленный в критерии.
3. Оценку нельзя выставить по критерию, которого нет в рубрикаторе.
4. Нельзя иметь две оценки по одному критерию.

### Domain Service
`TotalScoreCalculator` — сервис для подсчета итогового балла.
* *Обоснование:* Формула `? (score/max)*weight` требует одновременного доступа к оценкам студента и весам критериев. Так как `Student` не должен знать о `Rubricator` (чтобы не нарушать границы), эта логика выносится в Domain Service.

### Работа с репозиториями и маппинг
Домен ничего не знает о хранении (Persistence Ignorance). В слое Infrastructure реализованы `JsonStudentRepository` и `JsonRubricatorRepository`.
* *Обоснование выбора Data Mapper:* C# не умеет напрямую сериализовать в JSON приватные списки и VO. Поэтому используются "тупые" классы `StudentDbModel` и `RubricatorDbModel`. При сохранении домен маппится в DbModel, при чтении — восстанавливается обратно с соблюдением всех инвариантов (VO создаются заново и валидируются).

## 3. Паттерны GoF (по одному из каждой группы)

1. **Порождающий — Factory (`EvaluationFactory`)**
   * *Проблема:* Нужно создать оценку, но предварительно проверить, что балл не превышает максимум критерия. Но `Student` не знает о `Rubricator`.
   * *Решение:* Фабрика принимает студента, рубрикатор и сырой балл. Она находит критерий, проверяет инвариант и создает `Evaluation`. Это единая точка создания с проверками.
2. **Поведенческий — Strategy (`ITotalScoreStrategy` / `WeightedSumStrategy`)**
   * *Проблема:* Формула расчета итога может измениться (например, вуз захочет отсекать баллы или использовать другую кривую).
   * *Решение:* `TotalScoreCalculator` делегирует расчет интерфейсу `ITotalScoreStrategy`. В DI-контейнере (`Program.cs`) подставляется `WeightedSumStrategy`. Смена правила не затронет домен.
3. **Поведенческий — Template Method (`BaseImportEvaluationsUseCase`)**
   * *Проблема:* Импорт может быть из CSV или JSON. Каркас (найти студента -> поставить оценку -> сохранить) одинаков, а парсинг разный.
   * *Решение:* Абстрактный класс задает скелет в методе `Execute()`, а метод `ParseFile()` переопределяется в наследнике `ImportCsvEvaluationsUseCase`.
4. **Структурный — Facade (`ConsoleMenu`)**
   * *Проблема:* Консоли не нужно знать про 10 Use Cases и то, как их достать из DI.
   * *Решение:* `ConsoleMenu` скрывает вызовы Use Cases за простыми методами меню (`AddStudent()`, `CalculateTotal()`).

## 4. DI-контейнер
Используется `Microsoft.Extensions.DependencyInjection`. Сборка графа зависимостей происходит в `Program.cs` (Composition Root). 

## 5. Тесты
Покрыты ключевые инварианты и Domain Service (xUnit).

## 6. Роль ИИ
ИИ выступал в роли ассистента для рутинных задач (написание шаблонного кода, настройка DI-контейнера, JSON-маппинг). Ключевые архитектурные решения — от проектирования границ агрегатов и инвариантов до выбора паттернов GoF — были спроектированы и реализованы мной самостоятельно.
